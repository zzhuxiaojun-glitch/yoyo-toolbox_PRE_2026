# yoyo_dev —— 跨项目开发规范

这是 yoyo（zzhuxiaojun）在多个项目反复确认下来的 8 条通用工作习惯。**与具体项目栈无关**，可带到任何项目使用。项目专属规范（Supabase、pnpm Node 版本、特定 Git Flow 等）不在这里，仍由各项目的 `CLAUDE.md` / 项目 memory 承载。

收到任务时先扫一眼下面哪几条适用，按它做。

---

## 1. 改 runtime 代码走 TDD 红绿灯

所有 runtime 代码改动遵循三步：

1. 🔴 **红灯**：先写一个会失败的测试，复现 bug 或定义新行为的期望
2. 🟢 **绿灯**：写最小实现让测试通过，不追求完美
3. ♻️ **重构**：测试保护下清理代码、抽函数、改名

**分层策略（决定要不要写自动化测试）**：
- **纯逻辑**（计算、转换、校验、解析）→ 下沉到独立 helper 函数 → 用 `node:test` + `node --test`（或项目既有测试框架）写单元测试。ROI 最高。
- **组件 / UI 层**（React 组件、页面交互）→ 不强求自动化测试，**手动验证为主**（起开发服务器点一遍）。jsdom 环境噪音多，自动化 ROI 低。
- **API Route / I/O 边界** → 能抽出的纯逻辑下沉 helper 测；I/O 边界手动或集成验证。

**How to apply**：收到「改 X 功能 / 修 Y bug」→ 先判断有没有可下沉的纯逻辑。有 → 先写 `*.test.ts` → 跑红 → 实现 → 跑绿 → 重构。纯组件交互 → 明确说「这部分手动验证」并列出验证步骤让用户点。

## 2. 全程中文叙述（过程 + 汇报）+ 汇报末尾固定两行

- **所有面向用户的叙述都用中文**——不只最终汇报，也包括**过程中的解释性叙述**：思考外显、工具调用之间的「我现在在查 X / 排除了 Y / 下一步验证 Z」这类 narration 全用中文。
- 代码 / 工件（注释、commit message、变量名、日志）和工具命令本身仍用英文/原文。
- 用中文叙述**不影响任务准度**（推理本身与叙述语言无关），用户已确认——所以默认就用中文，不要为"保准度"切回英文。
- **每次实质性结果输出后，末尾固定加两行**：
  - `当前位置`：现在处于什么状态 / 刚完成什么
  - `下一步`：接下来要做什么 / 在等用户什么决定

**Why**：用户中文母语、多任务并行，全程中文（含过程）能随时看懂在干嘛、到哪了，省去追问与回读。

---

## 3. PR 用中文写 title + body

创建 PR（`gh pr create`）时：

- **title**：中文
- **body**：中文（背景 / 改动点 / 测试情况都用中文）
- **commit message**：仍按 conventional-commits 英文（`feat(scope): …` / `fix(scope): …` / `refactor(scope): …`）

**Why**：用户和 reviewer 都是中文母语，PR 用中文沟通效率高；commit 保持英文是为了符合 conventional-commits 工具链。

```bash
gh pr create --title "<中文标题>" --body "<中文正文>"
```

## 4. Bash cwd 跨 user turn 会回弹 → 用绝对路径

Bash 工具的工作目录（cwd）**跨 user turn 会回弹**到项目主根目录，**不保持**上一个 turn 的 `cd` 状态（每个 turn 的 shell 从 profile 重新初始化，shell 状态不跨 turn 持久化）。

**症状**：在非主 worktree / 子目录工作时，上个 turn `cd` 进去了，这个 turn 开头又回到主根，导致 `>` 重定向、相对路径写文件全写错地方。

**How to apply**：
- **全程用绝对路径**（最稳，首选）；或
- 在非主 worktree / 子目录工作时，**每个 turn 开头先 `cd` 到目标目录**
- 写文件 / 重定向前先 `pwd` 确认 cwd

## 5. 并行多会话 / 多 worktree 的两个 git 坑

同一个 repo 被多会话 / 多 worktree 同时改时，有两个高频坑：

**坑 A：宽泛 `git add` 扫走别人改动**
- `git add -A` / `git add .` 会把**别的会话**正在改、还没提交的文件一起 staged 进来，commit 里混入别人半成品。
- **解决**：只 `git add <明确文件路径>`，**绝不用 `-A` / `.`**。

**坑 B：本地未 push 的 feature ref 被对方覆盖**
- 会话 A 在 `feature/x` 上 commit 了没 push，会话 B 也动同名分支并 push → A 的本地 commit 丢失。
- **解决**：新 feature commit 后**立刻 `git push -u origin <branch>`**。

**坑 C：泛化分支名被别的会话顺手复用 → 工作流交叉、PR 混杂、测试互扰**
- 起 feature 分支用了太泛的名字（如 `feat/online-source`），另一个会话顺手提交到同名分支 → 两条工作流挤进一条分支 / 一个 PR，彼此的半成品、失败测试互相干扰，无法独立 review / 合并。
- **解决**：
  1. 每条独立工作流用**唯一、带 scope 的分支名**（`feat/online-source-mihon-capabilities` 而非 `feat/online-source`）。
  2. **开工即 `git push -u origin <branch>` 占位**，声明这条分支的所有权（也兼顾坑 B）。
  3. 已被污染时：从 `main` 新建干净分支，`git cherry-pick <自己的提交…>` 把自己的工作摘出来单独开 PR——只要双方改的文件零重叠，cherry-pick 无冲突（先 `git show --name-only` 比对确认无重叠）。

**坑 D：`git add <明确路径…>` 里有一个路径无效，整条 add 作废、什么都没暂存**
- 例：某文件已经 `git rm` 过（已暂存删除），再把它写进 `git add` 列表 → `fatal: pathspec ... did not match`，其余几十个文件也**一个都没加进去**；如果后面用 `;` 接着 `git commit`，提交里就只有之前暂存的那一点东西，推上去的 main 直接构建失败。
- **解决**：add 和 commit 分两步；commit 前先看 `git add` 的退出码和 `git diff --cached --stat`（文件数对不对）；已 `git rm` 的文件不要再写进 add 列表。已推送的残缺提交不要 force-push 改历史，补一个提交说明原委即可。

**通用习惯**：每个 turn 开头 `git branch --show-current` 复核当前分支，确认没漂到别的分支；多会话时优先各自独立 worktree（`git worktree add`）彻底隔离。

## 6. 大批量同质任务走 /loop + status 断点续传

- **触发条件**：≥ 几十个**同质、互相独立**的工作单元（重复性 dispatch / 抽取 / 翻译 / OCR / 批处理）。
- **方式**：`/loop`（不带 interval，让模型自定步调）无人值守连续跑。
- **断点续传**：每个单元完成写 `status/<task_id>.json`（记 task_id + 完成状态），中断后从未完成的接着跑。
- **不适合**：异质任务、需要人判断的任务、互相有依赖的任务 → 这些别上 /loop。

**How to apply**：判断任务是否同质独立 + 数量够多 → 是 → 设计 `status/*.json` schema → `/loop` 跑。

---

## 7. 踩坑即记录到项目 memory，并优化后续做法

干活时一旦踩到**非显而易见的坑**（隐性约束、反直觉行为、环境噪音、工具误报、调试中试错才发现的根因），当场把「现象 + 根因 + 解决/规避方法」沉淀下来，而不是修完就忘。

**写哪里**：
- **项目专属的坑** → 写进该项目的 memory（`MEMORY.md` 索引 + 单文件），`type: project`，正文带 `**Why:**` / `**How to apply:**`。
- **跨项目通用的坑 / 工作习惯** → 回流到本 skill（yoyo_dev），新增一条编号习惯。
- 不值得记的：代码本身能读出来的结构、git 历史已有的、只对本次对话有意义的——这些别记。

**记录要点**：要记的是「**当时为什么会踩 + 下次怎么不踩**」，不是流水账。能改进做法的（换参数、换路径、换顺序、加校验）一并写进 How to apply。

**Why**：同一个坑不该踩第二次；隐性约束（如「列表过滤只能 return null 不能 filter，否则下标错位改错数据」）破坏后果常是**静默错误**，不记录下次还会中招。

**How to apply**：debug / 试错 / 被工具误报干扰之后 → 判断是项目专属还是通用 → 写对应 memory 或回流 skill → 更新索引行。

---

## 8. 时刻盯上下文水位，紧张了主动提示换会话并给开工词

长任务里**持续自检上下文余量**，不要闷头干到被动截断或质量下滑。

**触发提示的信号**：上下文用量明显偏高（粗估 ≥ 七八成）、工具结果/注入噪音堆积、或任务还长但余量见底。

**提示动作**：
1. 明确告诉用户「上下文偏紧，建议换个新会话继续」。
2. 给一段**可直接粘贴的开工词**（接力 prompt）：包含当前进度、改了哪些文件、下一步要做什么、相关 job/路径/分支等关键上下文，让新会话无缝接上。
3. 余量健康时也在汇报里**简短报一下水位**（如「上下文健康，约用掉三成」），让用户心里有数。

**Why**：用户多任务并行，需要由我主动管理上下文健康度并在合适时机交接，而不是等卡死了才发现。开工词省去用户重新交代背景。

**How to apply**：每轮实质汇报时扫一眼水位 → 紧张 → 按上面三步提示 + 给开工词；健康 → 一句话带过。

## 适用边界

- ✅ 适用：写/改代码、修 bug、建 PR、跑批量任务、多会话或多 worktree 协作、向用户汇报。
- ❌ 不在本 skill：项目专属技术栈规范（数据库迁移约定、包管理器/Node 版本、特定分支策略、特定翻译风格）—— 那些看各项目 `CLAUDE.md`。
